# Development

## Build and test

Use the repository wrapper; it runs Go commands in rootless Podman. Tests are offline, mount source read-only and use a temporary filesystem. Do not run Go tests or builds directly on the host.

```sh
bash ./build.sh test   # go vet ./... and go test ./... -count=1
bash ./build.sh build  # Linux amd64/arm64 and macOS arm64 binaries in dist/
bash ./build.sh deps   # networked module tidy/download; only after vetting a dependency
```

`deps` is the only networked wrapper operation. The project uses the pinned dependencies in `go.mod`; do not add a package without reviewing its source and dependency graph.

## Package map

- `cmd/nod`, `internal/cli`: entry point, command registration, flag parsing and exit behavior.
- `internal/config`, `internal/state`, `internal/install`: configuration paths, rollback record and inspectable installation plan.
- `internal/models`, `internal/modelscli`, `internal/llamacpp`: the model catalogue (URLs, sizes, checksums, conversion steps), `nod models list|verify|sidecar`, and locating the user's llama.cpp libraries. Nothing here downloads.
- `internal/server`, `internal/client`, `internal/decider`: HTTP endpoints/client, model lifecycle and inference bridge.
- `internal/engine/{tiers,rules,pipeline,conversation,prompt,classify}`: deterministic call tiers, rules, decision pipeline, context and classification.
- `internal/hosts`, `internal/hosts/{claude,hermes,pi,opencode}`, `internal/hooksintegration`, `internal/transcript`: host wiring, hook commands and transcript filtering.
- `internal/service`, `internal/doctor`, `internal/decisionlog`, `internal/skill`: user service, diagnostics, RAM-backed verdict log and agent guidance.

## Golden data and parity

`testdata/golden/` contains synthetic reference outputs used by deterministic parity tests. It is generated by `tools/gen_golden.py` from the read-only Python reference tree. Treat these files as test inputs: do not regenerate or hand-edit them as part of ordinary development. A change to expected behavior needs a reviewed reference/golden update and corresponding Go tests.

For real-hardware validation, use a pinned model and llama.cpp runtime, then compare `/decide` outputs with `testdata/golden/decider_4b_q4km.json`. A parity script should submit identical context/schema inputs to both implementations, compare decisions and probability fields with the documented tolerance, and record model hash, runtime build, hardware and latency. Do not use live user conversations or secrets as fixtures. Model loading, GPU selection and performance cannot be established by the offline unit suite.

## Limits

- Same-uid code can alter nod's binary, config, service or hooks. This is a gate, not a sandbox.
- Hermes and Pi integrations are embedded host-side plugin/extension assets; their runtime and UI behavior follows those hosts. Verify them in an isolated real host session before relying on them.
- opencode: the plugin `internal/hosts/assets/opencode/nod.js` is maintained here; its Node unit tests are in `internal/hosts/opencode/testdata/` (`podman run --rm --network=none --read-only --tmpfs /tmp -v "$PWD":/src:ro -w /src docker.io/library/node:22 node --test internal/hosts/opencode/testdata/nod.test.mjs`). It has not been run against a real opencode.
- HTTP serving has no authentication or TLS. Keep it on loopback or a private network.
